# 코드 리뷰 노트: 연구 코드 → 정리본

연구 단계의 코드(`trademark_risk_v9/src`)는 결과는 맞지만 읽기 어려웠습니다. 무엇이 문제였고
어떻게 바꿨는지, 그리고 바꾸지 않은 것은 무엇인지 적습니다.

## 발견한 문제와 조치

| # | 문제 | 예 | 조치 |
|---|---|---|---|
| 1 | **버전 폴더 간 사슬 의존.** v9가 v8 → v7 → v6 → v3 코드를 `sys.path.insert`로 끌어다 씀. v9 폴더만으로는 실행 불가 | `sys.path.insert(0, ROOT/'trademark_risk_v8/src')` | 실제 실행 경로에 있는 코드만 모아 하나의 패키지로 재구성 |

| 4 | **한 줄에 여러 문장**, 최대 565자, 한 글자 변수(`d`, `f`, `p`, `b`, `q`, `a`) | `fit=...;cal=...;val=...;y=...` | 한 줄 한 문장, 의미 있는 이름, 140자 제한(ruff) |

## 바꾸지 않은 것

계산 결과에 영향을 주는 것은 하나도 바꾸지 않았습니다.

- 정규화, n-gram, 후보 선정(512건 상한, 동점 처리), 유사도 가중치(0.65/0.35, 0.6/0.4, 0.95, 세제곱)
- 특징 32개의 정의와 순서
- XGBoost·로지스틱 회귀·보정 설정, 혼합 비율, 검토 권고선 계산
- `pair_search.py`의 rapidfuzz 유사도는 원 코드처럼 float32 정밀도를 유지했습니다. float64로
  '고치면' 특징값이 미세하게 달라져 동결 모델과 어긋납니다. 주석으로 이유를 남겼습니다.

동일성은 `scripts/check_against_frozen_v9.py`로 실제 자료에서 확인했습니다(README의 표).

## 정리본에 넣지 않은 것

| 항목 | 이유 |
|---|---|
| 라벨 표·TF-IDF를 만드는 단계(v1·v3·v6의 준비 코드) | 원자료와 이전 버전 산출물 여러 개에 걸쳐 있어 독립적으로 재현·검증할 수 없었음. 규칙은 버전 히스토리에 서술하고 산출물을 입력으로 받음 |
| v6·v7·v8 모델을 다시 실행해 비교하는 코드 | 이전 버전의 모델 파일과 코드가 필요. `evaluate.run(baselines=…)`에 저장된 예측을 넘겨 비교하는 방식으로 대체 |
| 새 평가자료 채점 시 v6·v7·v8 대비 개선 구간 검사 | 위와 같은 이유. 입장 심사·출처 확인·1회 채점·ROC 기준은 유지. 전체 배포 조건은 연구 작업 폴더의 `protocol.json`이 기준 |
| 5건 사례 비교, HTML 보고서 생성 | 특정 파일 경로·출원번호에 묶인 일회성 분석 |
| 공고일 미확인 목록(약 21만 행) CSV 출력 | 건수만 감사 기록에 남김 |

## 알고 있는 개선 여지

- 색인 파일이 약 1.1GB이고 저장할 때 메모리를 6GB 이상 씁니다. 원인은 지정상품 원문을 담은 표와
  작은 배열 수십만 개를 통째로 pickle하는 구조입니다. 역색인을 '하나의 큰 배열 + 오프셋'으로 바꾸면
  줄일 수 있습니다.
- 지정상품 겹침은 문자 일치 기준입니다. 유사군코드를 상품별로 대응시킨 자료가 있으면 더 정확해집니다.
- `fresh_evaluation.known_identities`는 풀과 라벨 표만 봅니다. 연구 코드는 심사문서 지식 DB에 등장한
  출원번호까지 차단했습니다(해당 출원은 모두 풀에 포함되어 있어 현재 자료에서는 결과가 같습니다).
